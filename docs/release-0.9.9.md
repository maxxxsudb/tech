# 0.9.9 — уведомления, SQL-изменения и сохраняемые расследования

Выбранный приоритетный срез: E9 → C3/E11 + B3/C2 → B1. Основные четыре действия чата сохранены; новые формы свёрнуты. Изображения, OCR и транспорт не менялись. Это не завершение всего блока 6.

## Почему не пришло уведомление

На странице Alerting в «Состав и свежесть данных» появился отдельный разбор конкретного экземпляра. Кнопка явно читает встроенный Grafana Alertmanager: instances, groups, effective config, silences, policies, contact-point names/types и mute timings. Datasource-запросов и записи нет. Ошибка/403 остаётся неизвестностью, а не пустым списком.

Расчёт использует реальные labels выбранного fingerprint. Показаны наблюдаемые receivers из API, путь совпадений с nested/continue/fallback, наследуемые grouping/timer настройки, mute/active intervals. Effective config предпочтительнее статических policies: в ней видны сгенерированные маршруты. При её недоступности fallback на provisioning помечается ограниченным. Настройки и адреса каналов не включаются в evidence.

`status.silencedBy`, `status.inhibitedBy` и при наличии `mutedBy` — факты ответа Alertmanager. Для silence показывается найденная запись, для inhibition — источник по fingerprint, если он доступен. Сопоставление маршрутов и временных окон помечено расчётом. Состояние unprocessed и недоступные API видны отдельно. Экспорт JSON и передача отчёта модели — по кнопке, с сохранением этих различий.

Доставка всегда `unknown`: receiver/маршрут не доказывают отправку или получение. Журнал доставки, ошибки внешнего канала, очередь и история scheduler здесь не прочитаны. group_wait/group_interval/repeat_interval показаны как конфигурация, без вычисления вымышленного времени отправки. API читаются не атомарно; временные расчёты привязаны к loadedAt. Снимок старше 5 минут требует обновления. Историческая недоставка не объясняется текущим снимком.

Поддержаны equality/negative, отсутствующий label как пустой и консервативное подмножество regex. Сложный RE2/небезопасный для JS pattern даёт partial; наблюдаемый receiver API при этом остаётся доступен. Внешние Alertmanager не поддержаны. Полное исполнение любого RE2 в браузере и доказательство доставки не заявляются.

## Что изменилось перед срабатыванием

В «Действия → Расследования и кейсы» доступно сравнение сохранённых версий связанного dashboard. По времени инцидента выбирается самая новая доступная версия строго раньше этого момента; без времени — предыдущая доступная версия. На Alerting время предлагается из startsAt экземпляров и редактируется. Нет старой версии/неизвестны даты/403 — явная ошибка, без утверждения об отсутствии изменений.

Сравниваются сохранённые SQL/targets, datasource, настройки панели, добавленные/удалённые/вложенные панели и переменные. SQL показывается построчно. Есть ссылка на текущую панель, JSON export и объяснение модели. Перед сравнением и после чтения сверяется текущая версия; гонка требует повтора. Никаких datasource-запросов или записи.

Границы: до 1000 доступных версий, 50 изменённых панелей в подробном выводе, 2000 символов на сторону поля/SQL и 100 строк diff; обрезка помечается. Версии с отсутствующими/повторными ID панелей не сравниваются как достоверные. Сравнение с текущей версией может включать правки **после** начала инцидента. Сохранённый SQL панели и SQL alert-rule могут различаться. Изменения БД/приложения, несохранённые правки и настоящая история alert-rule сюда не входят. Корреляция не считается причиной.

## Кейсы

Там же — явное локальное сохранение текущего расследования. Opt-in выключен при открытии. Нет автоматического постоянного сохранения: штатная session-история работает как прежде. Хранилище разделено по origin, Grafana subpath, org и пользователю. До 20 кейсов, 200 КБ UTF-8 на кейс, 2 МБ суммарно. Переполнение/повреждение показывается ошибкой; старые кейсы молча не удаляются.

Кейс содержит название, время, исходный dashboard/alert/panel, абсолютный период последнего вопроса, отдельно диапазон на момент сохранения, переменные, текущие тексты выбранных запросов, диалог и явно полученные evidence уведомлений/версий. Каждый новый вопрос сохраняет свои sentAt/absoluteRange; относительный `now-1h` не сдвигает сохранённый кейс в будущее. SQL на момент сохранения не объявляется доказательством выполнения или точным текстом старого запроса. Изображения/base64/вложения, executable action и внутренние modelContent исключены; применяется существующий sanitizer чувствительных полей. SQL/labels/текст могут содержать рабочие данные — это прямо указано перед opt-in.

Доступны поиск по названию/UID, просмотр исходного evidence, переименование, удаление, JSON export/import с новым ID и подтверждённая очистка собственных кейсов. Восстановление заменяет текст диалога только в соответствующем контексте; для другого dashboard/alert/panel/Explore URL оно заблокировано. Новых запросов и действий нет. Datasource snapshot не восстанавливается: старые сообщения помечаются исходным периодом, новые запросы используют текущий контекст.

Индекс-аннотация — отдельный preview с подтверждением Editor/Admin. В Grafana пишутся краткая сводка и ID с тегами `tech-ai-case`/`ai-assistant`/`alert:<uid>`. Полный кейс остаётся в исходном браузере: другой пользователь не может восстановить его по одному ID. Очистка локального хранилища не удаляет аннотации. Это не командное серверное хранилище и не state history.

## SQL-плейбуки

В существующих «Других сценариях» добавлены «Проверить SQL-алерт», «Разобрать ошибку PostgreSQL» и «Сравнить SQL-периоды». Они используют текущий выбор панели и существующие подтверждения расследования; права на query/schema отдельно не включаются.

В Configuration можно задать до 12 командных сценариев `{label,prompt,needsPanel?,sampleData?,investigation?,comparePeriods?}`. Проверяются размер, дубли и типы; неизвестные поля запрещены. Невалидное сохранённое значение не ломает чат. comparePeriods открывает параметры расследования. Это текстовые сценарии, не универсальный исполняемый runbook-движок.

## Проверки

Прогон `node test/verify-incident-priorities-live.cjs` использует существующие PostgreSQL 16.15/Grafana 13.2.2. Реальное SQL-правило временно включается **после** установки точного тестового silence; реальный scheduler передаёт срабатывание в Alertmanager. Проверяются suppression/receiver/unknown delivery, настоящие версии SQL/переменных, UI evidence, opt-in и восстановление после reload, индекс-аннотация и мобильный UI. Inhibition/nested/regex/mute/403 проверяются в unit; конфигурация policies/contact points на стенде не меняется. Интеграционный сценарий полного Assistant подменяет только модель/настройки в браузере; остальные успешные API настоящие. Все временные серверные ресурсы удаляются, активный экземпляр разрешается перед завершением тестового silence. Итоги и хеши — в [плане](implementation-blocks.md).

Основание семантики: [notification policies](https://grafana.com/docs/grafana/latest/alerting/fundamentals/notifications/notification-policies/), [Alertmanager route/time/inhibition](https://prometheus.io/docs/alerting/latest/configuration/), [Alertmanager API schema](https://github.com/prometheus/alertmanager/blob/main/api/v2/openapi.yaml), [dashboard versions API](https://grafana.com/docs/grafana/latest/developer-resources/api-reference/http-api/api-legacy/dashboard_versions/).

Отложены: ранжирование/аномалии B2, анализ шума по настоящей state history E12, coverage E13 и универсальные исполняемые runbooks C5. Полностью пустой alert-builder без панели пока не добавлен; существующие panel-builder и импорт сохранены.
