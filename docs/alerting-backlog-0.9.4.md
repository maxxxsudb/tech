# Alert-centric extension — Tech AI Assistant 0.9.4

**Дата:** 2026-10-19  
**Связь с основным бэклогом:** дополняет [backlog-0.9.4-review.md](backlog-0.9.4-review.md). Если алерты становятся приоритетом №1, трек E заменяет пункты C1–C3 и меняет порядок остальных.  
**Ограничение:** по-прежнему frontend-only, без нового backend, БД и серверного хранилища. Все операции — через существующие API Grafana и Alertmanager.

---

## 1. Тезис

Сейчас плагин — «чат с контекстом дашборда». Если приоритет алерты, продукт должен стать **alert lifecycle copilot**: 

**создать → проверить на истории → выкатить безопасно → разобрать срабатывание → настроить → замолчать → разобрать постфактум.**

Это не «ещё одна кнопка в Alerting UI». Это слой, который:
- превращает панель или текстовое намерение в валидное правило;
- проверяет правило на прошлых данных до включения;
- объясняет, почему алерт шумит или молчит;
- помогает дежурному разобрать срабатывание;
- сохраняет результат как кейс/аннотацию;
- не делает необратимых действий без подтверждения.

Ключевое отличие от «просто генерации YAML моделью»: **детерминированный builder + валидация + backtest + diff + audit**, а модель отвечает за намерение и объяснение, не за сырой JSON.

---

## 2. Что меняется в приоритетах

Если алерты — главный сценарий:

- **C1 (alert-first контекст)** становится частью **E2 (triage)**.
- **C2 (кейсы)** остаётся, но становится хранилищем для E2/E11.
- **C3 (diff версий)** становится частью E2/E11.
- **A1 (контекст при смене дашборда)**, **A3 (CI)**, **A4 (prompt injection)** остаются P0-предпосылками.
- **B2 (context intelligence)** и **B3 (persistence)** — усилители triage и кейсов.
- **B1 (prompt library)**, **D1 (vision)**, **C6 (multi-dashboard)** уходят на второй план.
- Новый трек **E** — основная линия.

## 3. Модель безопасности (читать до всех E-пунктов)

Запись в Alerting — это пейджинг, дежурные и потенциально необратимые действия. Поэтому:

1. **Никаких автономных записей.** Создание, изменение, удаление, silence — только после явного подтверждения с diff/preview.
2. **Новые правила создаются `isPaused: true`.** Включение — отдельное подтверждённое действие. Это дефолт, пока команда не решит иначе.
3. **Provisioned rules не редактируются.** Если `provenance` не пустой — только просмотр, diff и экспорт YAML-патча. Не пытаться обойти API.
4. **Dry-run и валидация до записи.** Builder → локальная валидация схемы → preview/test endpoint → backtest → diff → подтверждение → запись.
5. **Blast radius виден.** Перед записью: folder/group, labels, маршрут уведомлений, число правил в группе, оценка нагрузки. Для удаления — typed confirmation.
6. **Audit log локально.** Кто, когда, что создал/изменил/замолчал, before/after JSON; экспорт. Без секретов.
7. **Silence с ограничениями.** Максимальная длительность (например, 7 дней), обязательный комментарий, preview затронутых алертов, никакого авто-silence.
8. **Никаких записей contact points и notification policies в v1.** Это слишком высокий blast radius. Только чтение и объяснение.
9. **Честные ограничения backtest.** Поддерживаются простые условия (query → reduce → threshold). Сложные выражения помечаются «не поддержано», а не аппроксимируются молча.
10. **Права проверяются на входе.** Viewer — read-only; Editor/Admin — запись, если API разрешает. При 403 — понятный read-only режим, а не «сломалось».
11. **Тесты только на non-prod.** E2E: создать paused → preview → удалить. Unit — с замоканным API.
12. **Никакой авто-ремедиации.** Плагин не перезапускает поды, не меняет пороги без подтверждения и не «чинит» алерты сам.

## 4. API и архитектура (проверить на Grafana 13.2.2)

- **Правила и состояние:** `GET /api/prometheus/grafana/api/v1/rules`, `GET /api/alertmanager/grafana/api/v2/alerts`.
- **CRUD правил:** `/api/v1/provisioning/alert-rules` (тот же API, который использует UI Alerting; точные методы и права проверить).
- **Экспорт:** `/api/v1/provisioning/alert-rules/export`.
- **Contact points / policies / mute timings:** `/api/v1/provisioning/contact-points`, `/api/v1/provisioning/notification-policies`, `/api/v1/provisioning/mute-timings` — только чтение в v1.
- **Silences:** `GET/POST/DELETE /api/alertmanager/grafana/api/v2/silences`.
- **Folders / rule groups:** `/api/folders` и API групп правил; проверить, создаётся ли группа неявно при создании правила.
- **Preview/test правила:** endpoint, который использует UI Grafana; точный путь проверить. Fallback — выполнить запросы через `/api/ds/query` и посчитать условие на клиенте.
- **State history:** Grafana Alerting State History хранится в Loki; если он настроен, читать через datasource. Иначе — `ALERTS`/`ALERTS_FOR_STATE` (если доступны) или локальный audit; честно писать об ограничении.
- **Роли:** чтение правил/алертов — Viewer; создание/изменение — Editor/Admin в зависимости от RBAC; silences — отдельное право. Проверить матрицу.
- **Provisioning:** поле `provenance`; правила из файлов могут быть защищены от API-изменений.
- **Схема правила:** `folderUID`, `ruleGroup`, `orgID`, `condition`, `data[]` (queries + expressions), `noDataState`, `execErrState`, `for`, `labels`, `annotations`, `isPaused`, `title`, `uid` при обновлении.

**Вывод:** нужен отдельный модуль `alerting.js` с типами, builder’ом, валидатором, API-клиентом, diff/audit и permission/provenance-гейтами. Сырой JSON от модели в API не отправляется.

## 5. Новые пункты

### E1. Alert domain layer и примитивы безопасности
- **P0 · M · ценность 5 · риск 3**
- **Сейчас.** Нет ни одного alert-API, модели правила, валидации, diff или audit.
- **Сделать.** Модуль `alerting.js`: загрузка правил/алертов/folders/contact points/policies/mute timings; типы `AlertDraft`, `AlertAudit`, `BacktestResult`, `SilenceDraft`; builder правила; валидатор refId/condition/data; `provenance`; permission gate; diff; audit log; feature flags. В этом пункте — без UI-записей.
- **Зачем.** Все остальные E-пункты не должны изобретать свою работу с API и свою безопасность.
- **Приёмка.** Читает правила и алерты; валидирует черновик; показывает diff; пишет audit; при 403 переходит в read-only; ни одной записи.
- **Зависит от:** A1, A4.

### E2. Triage сработавшего алерта
- **P0 · M–L · ценность 5 · риск 3**
- **Сейчас.** На страницах алертов контекста нет: `loadContext` выходит без dashboard UID.
- **Сделать.** Детект `/alerting/...`; правило, активные алерты, labels/annotations (`summary`, `runbook_url`, `dashboardUid`, `panelId`), `startsAt`; связанный дашборд/панель; диапазон вокруг `startsAt`; карточка и «Разобрать алерт»; контракт ответа (что сработало, когда, evidence, гипотезы, что проверить, действие); ссылка на runbook; сохранение кейса.
- **Зачем.** Главный сценарий дежурного; плагин перестаёт быть «чатом про дашборды».
- **Приёмка.** С страницы горящего алерта один клик; до подтверждения нет запросов к datasource; ответ называет алерт/диапазон/evidence; работает без linked dashboard.
- **Зависит от:** E1.

### E3. Аудит и quality score правил
- **P0 · M · ценность 5 · риск 4 (read-only)**

Score, таблица, фильтры, экспорт Markdown/JSON. AI объясняет issue и предлагает fix-draft, но не применяет.

- Редактирование provisioned rules через API.
- Запись contact points и notification policies в v1.
- Замена Alerting UI и полноценный редактор правил.
- Авто-ремедиация и запуск runbook-действий.
- Генерация сырого Grafana JSON моделью без builder’а и валидации.
- Обещание backtest для сложных выражений, которые не поддержаны.
- Собственный backend для state history.
- Поддержка всех datasource сразу: начать с Prometheus/Loki, SQL — после проверки.

6. Есть ли non-prod Grafana с Alerting для e2e?
7. Не переоценён ли backtest: может, важнее аудит и triage, а создание — позже?
